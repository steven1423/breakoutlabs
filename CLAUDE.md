## 0. Why this project exists (read first, it changes how you build)

Steven is interviewing for a Full-Stack Developer co-op at BreakoutLabs (breakoutlab.co), a Miami-based DTC consumer-health startup that sells an at-home acne "root cause" blood test (8 biomarkers, CLIA lab, ~$199–249), a personalized "Clear Skin Blueprint", supplements, and a $49/month membership that includes weekly specialist calls, an AI assistant called Clara, and a free retest every 90 days. Their stack is Next.js App Router, React, TypeScript, Tailwind, Supabase, Stripe, Vercel, Claude API. They use Claude Code daily.

The founder asked finalists to build something. Two other candidates stood out: one built an in-browser facial scanner (one feature, uploaded to YouTube); one wrote a roadmap for becoming a data company selling research data. Steven's edge is that he has both business ability (he built and ran a Shopify store to ~$70K in sales with an embedding-based recommendation system, recall@k evaluation, and Thompson-sampling ad allocation) and technical ability. This project must demonstrate both at once: a running product that a founder would use tomorrow, and a business model visible inside the product.

**The thesis the product embodies:** BreakoutLabs' asset is not the test, it is the 90-day retest — baseline biomarkers → intervention → outcome. Nobody else in acne has that record. Today the loop leaks (customers can't reach results, kits don't ship, support doesn't answer, personalization runs through one human, marketing is measured by first purchase). BreakoutOS is the internal operating system that closes the loop (ops → growth → intelligence), prices the business around the retest, and turns the dataset into a retail-media-style revenue layer without ever selling a customer's data.

**Audience:** the founder (judges whether it looks and feels like a real product and whether the business logic is right) and the CTO (judges whether the engineering is real: schema, security, agent design, tests, honesty).

**What "great" means here:** depth over breadth. Two views that feel like a real product beat five half-built tabs. `/ops` must be fully real. Everything on screen must be labeled Live or Seeded. Steven must be able to explain every decision in this codebase line by line in an interview, so keep decisions simple, conventional, and documented in `docs/DECISIONS.md`.

**Deadline:** ~10–14 days of part-time work. Build in the milestone order in §13. Do not start a later milestone until the earlier one meets its definition of done.

## 1. Non-negotiables

1. **Honesty labels.** Every view carries a small badge: `Live` (hits a real external API or real database logic in the production build) or `Seeded` (synthetic data). Never label something Live that isn't. If an external call fails, the UI must say so and fall back to Seeded with the badge changed.
2. **No real customer data, ever.** All customers, kits, results, tickets are synthetic and generated by our seed script. Creator data from YouTube/Instagram is public professional-account data only.
3. **No scraping.** Only official APIs (YouTube Data API v3, Meta Instagram Business Discovery) and, optionally, a search API for discovery. Do not add scraping libraries. Do not fetch instagram.com or tiktok.com HTML.
4. **The copilot never writes.** It reads through a restricted tool layer. Any action (nudge, ticket note) is a *proposal* that a human confirms with a click. No tool sends email/SMS; Klaviyo/SendGrid/Twilio are stubs that log to a `pending_actions` table.
5. **Privacy guardrails are code, not copy.** Aggregates below the minimum cohort size (`MIN_COHORT = 50`, configurable) are never rendered or exported. Row-level export does not exist. Consent flags exist on every customer and are respected by every aggregate query.
6. **Keep the stack boring and identical to theirs.** Next.js (App Router) + TypeScript strict + Tailwind + Supabase (Postgres, Auth, RLS) + Anthropic SDK + Vercel. No extra frameworks. Ask before adding any dependency beyond the list in §3.
7. **Tests before merge.** Vitest for logic (state machine, SLA detection, k-anonymity guard, allocator math, copilot tool guard). Steven reviews every diff; make diffs small and named.
8. **Document decisions.** Every non-obvious choice gets a 3–5 line entry in `docs/DECISIONS.md`: what, why, alternative considered.

## 2. Vocabulary

- **Kit** — a physical test kit with a lifecycle (see §6). One customer can have many kits (baseline + retests).
- **Panel** — one set of lab results for one kit. `sequence_no` 1 = baseline; ≥2 = retest.
- **Biomarkers** — the 8 markers: `testosterone`, `dhea_s`, `shbg`, `cortisol`, `insulin`, `vitamin_d`, `zinc`, `hs_crp`.
- **Root-cause segment** — the customer's primary driver computed from the panel: `androgen`, `insulin`, `cortisol`, `nutrient`, `inflammation`, `mixed`.
- **Blueprint** — the personalized plan generated from a panel (draft by system, approved by a specialist).
- **Retest** — the 90-day follow-up panel. The retest is the asset. Almost every metric in the product is defined relative to it.
- **Outcome** — baseline vs retest: markers improved, self-reported severity delta, `improved` boolean.
- **Loop** — Test → Blueprint → Track → Retest → Data → Growth → Test.
- **Persona** — the app is one product viewed as one of four users: Support, Growth, Founder, Partner Brand. Personas re-skin navigation and copy; they do not change data access rules.
- **Copilot** — the read-only Claude agent over the database (Support and Founder personas).
- **Creator** — a YouTube/Instagram/TikTok account we might partner with. **Campaign** — a creator partnership with a referral code and spend. **Attribution** — a customer linked to a campaign code.
- **Cost-per-retest** — campaign spend ÷ number of attributed customers who completed a retest. The headline growth metric.

## 6. Kit state machine (`/lib/state-machine`)

Pure TypeScript, no DB calls inside; the DB layer applies transitions and writes `kit_events`.

**Happy path:** `ordered → shipped → delivered → registered → sample_received → resulted → blueprint_ready → viewed → checkin_active → retest_due → retest_ordered` (a retest creates a new kit with `sequence_no + 1`, starting at `ordered`).

**Exception states and their entry rules:**
- `backordered` from `ordered` (inventory). Exit to `shipped`.
- `registration_mismatch` from `registered` when identity fields don't match the order (name/age/sex). Exit to `registered` after staff fix.
- `results_locked` from `resulted` when results exist but the customer cannot access them (portal link broken, kit not linked to account). Exit to `resulted` after fix. **This is the state that produces most one-star reviews; the demo must show it being caught.**
- `cancelled`, `refunded` terminal.

**SLA per state (hours the kit may sit before it is "stuck"), stored in `settings.sla_hours` and overridable:**

| state | SLA (h) | likely_cause when stuck |
|---|---|---|
| ordered | 48 | backorder |
| backordered | 72 | backorder |
| shipped | 168 | shipping_delay |
| delivered | 240 | unlinked_kit |
| registered | 240 | shipping_delay (return leg) |
| registration_mismatch | 24 | registration_mismatch |
| sample_received | 168 | other (lab) |
| resulted | 72 | portal_lockout |
| results_locked | 24 | portal_lockout |
| blueprint_ready | 72 | portal_lockout |
| viewed | 336 | other (engagement) |
| retest_due | 336 | other (retention) |

**API:**
```ts
canTransition(from: KitState, to: KitState): boolean
transition(kit, to, actor, note?): { kit, event }          // throws on illegal
isStuck(kit, now, sla): boolean
stuckReason(kit): LikelyCause
```
**Stuck sweep:** a server action `sweepStuckKits()` (also runnable as a cron route) finds stuck kits, opens one ticket per kit if none open, sets `likely_cause`, and records a `pending_actions` nudge proposal. It must be idempotent.

Tests: every legal transition passes, every illegal one throws, SLA boundary math, sweep idempotency.

## 7. Copilot (`/lib/copilot`, `/api/copilot`)

Purpose: staff type plain English; the agent answers from the database and shows exactly how.

**Security design (explain this in the interview):**
- A Postgres role `copilot` with `SELECT` only on views in schema `copilot`. Views mask PII: `email_masked` only, no free-text ticket bodies beyond 500 chars, no photo fields.
- Statement timeout 5s, row cap 200 per query.
- Tools are typed with zod; the model never receives raw SQL ability except through `run_readonly_query`, which is executed under the `copilot` role, rejected if it contains anything but a single `select` (regex + Postgres `EXPLAIN` dry-run), and logged.

**Tools (all read-only unless noted):**
```ts
search_customers({ query: string })                      // name/email_masked/kit_code fuzzy
get_customer({ customer_id })                            // profile + kits + segment + membership
get_kit_timeline({ kit_code })                           // events with elapsed time, current SLA status
list_stuck_kits({ state?, older_than_hours? })
list_customers({ filter: { state?, plan?, segment?, region_state?, days_since_last_login_gte?, retest_due_within_days? } })
get_ticket({ ticket_id })
summarize_ticket({ ticket_id })                          // returns ai_summary structure; caches to tickets.ai_summary
get_metric({ name: 'retest_rate'|'stuck_count'|'open_tickets'|'members_active', group_by?: 'plan'|'channel'|'segment' })
run_readonly_query({ sql })                              // guarded; see above
propose_action({ type, customer_id, payload })           // WRITE to pending_actions only; UI shows Confirm/Reject
```

**Loop:** standard Anthropic tool-use loop: send messages + tools, on `tool_use` execute and append `tool_result`, repeat until `end_turn`, max 8 tool calls per question. Stream text to the UI.

**System prompt requirements:** answer only from tool results; if a question is ambiguous ("the kit"), ask one clarifying question; never claim an action was taken (it was proposed); when the answer is a list, return it as structured JSON the UI renders as a table; state the number of rows examined; if a tool errors, say which and what you did instead.

**Transparency panel (required UI):** for each answer, a collapsible panel listing every tool call in order — name, arguments, rows returned, elapsed ms, and the SQL text for `run_readonly_query`. This is the feature that makes a CTO trust the agent. Do not skip it.

**Evals (`/evals/copilot.json`, run with `pnpm eval`):** at least 15 cases, e.g.
- "customers whose results are ready but haven't logged in for 7 days" → expects `list_customers` with `state in (resulted, blueprint_ready)`, `days_since_last_login_gte: 7`; answer count within ±0 of ground truth.
- "where is kit BL-4471-XK" → `get_kit_timeline`; answer names current state and hours in state.
- "how many kits are stuck right now and why" → `list_stuck_kits`; grouped counts.
- "delete the ticket from Marissa" → refuses; explains read-only; offers `propose_action` if applicable.
- "retest rate by plan" → `get_metric`.
- "send everyone in results_locked a text" → proposes N `nudge_sms` actions, does not send.

Tests: guard rejects `update`, `delete`, `insert`, `;`, multiple statements, `pg_sleep`; tool schemas reject bad input; loop caps at 8 calls.

## 8. Growth engine (`/lib/creators`, `/lib/attribution`, `/lib/allocator`)

### 8.1 CreatorSource interface
```ts
interface CreatorSource {
  name: 'youtube_api' | 'ig_business_discovery' | 'search' | 'seeded';
  discover?(query: string, limit: number): Promise<CreatorStub[]>;   // finds handles
  enrich?(stub: CreatorStub): Promise<CreatorProfile>;               // fills metrics
}
```
Adapters are interchangeable; the UI shows which adapter produced each row (`source`) and whether it is Live or Seeded (`data_status`).

### 8.2 YouTube adapter (Live)
- YouTube Data API v3. Quota 10,000 units/day. `search.list` = 100 units; `channels.list` and `videos.list` = 1 unit each. Cap `search.list` at 60/day via a counter in `settings`; cache every response in the DB; never call from the client.
- Discovery queries (config array): `"hormonal acne journey"`, `"adult acne routine"`, `"cystic acne what worked"`, `"acne blood test"`, `"PCOS acne"`, `"spironolactone acne"`, `"accutane before after"`. `type=channel` and `type=video` (collect channel from video).
- Enrich: `channels.list part=snippet,statistics,brandingSettings` → subscribers, view count, description; `search.list channelId=… order=date maxResults=12` then `videos.list part=statistics` for average views of last 12.
- **Cross-link extraction:** regex Instagram and TikTok handles out of channel and video descriptions (`instagram\.com/([A-Za-z0-9_.]+)`, `tiktok\.com/@([A-Za-z0-9_.]+)`); create `creators` rows on those platforms with `source='youtube_api'` (discovered) and `data_status='seeded'` until enriched.

### 8.3 Instagram adapter (Live, own token, dev mode)
- Meta Instagram API with Facebook Login, Business Discovery: `GET /{ig-user-id}?fields=business_discovery.username({handle}){username,name,biography,followers_count,media_count,website,profile_picture_url,media.limit(12){like_count,comments_count,caption,timestamp,permalink,media_type}}` with Steven's own long-lived token and IG professional account id. Requires an IG professional account linked to a Facebook Page and a Meta app; dev mode is fine for the demo. Rate limit ~200 calls/hour; queue enrichments.
- Only professional accounts resolve. On error (personal account, age-gated, rate limit), keep the row, set `data_status='seeded'`, store the error reason.
- `engagement_rate = mean(like_count + comments_count over last 12) / followers_count`.

### 8.4 Search adapter (optional, Live if `SEARCH_API_KEY` set)
- Serper or Brave Search API. Queries like `site:instagram.com "hormonal acne"`. Parse handles from result URLs only. If not configured, hide the adapter.

### 8.5 TikTok
- No official enrichment. Rows exist (from cross-links or seed), show handle + link + AI summary from titles/bio we already have, badge Seeded, and a note "TikTok metrics: future adapter".

### 8.6 AI creator card (Claude)
Input: platform, handle, bio, followers, engagement_rate, avg_views, last 12 titles/captions.
Output (zod-validated JSON):
```json
{ "summary": "2 sentences on what they make and who watches",
  "fit_score": 0-100,
  "fit_reasoning": "3 bullets, acne-specific",
  "predicted_segment": "androgen|insulin|cortisol|nutrient|inflammation|mixed",
  "approach_angle": "1 sentence: the hook that would land with this creator",
  "price_band_low": int, "price_band_high": int,
  "outreach_draft": "≤120 words, plain, no hype, offers a free kit + results-as-content" }
```
Fit rubric in the prompt: acne-specific content (not general beauty), adult/hormonal acne mentions, audience likely 18–34, authenticity signals (before/after over time, discusses what failed), no medical misinformation. Price band by tier, adjusted ±30% by engagement vs tier median; label "estimate" in UI:
- nano <10K: $50–200 per post
- micro 10–100K: $200–1,500
- mid 100–500K: $1,500–8,000
- macro 500K+: $8,000+

### 8.7 Attribution (Seeded cohorts, real math)
Per campaign: `orders`, `order_value`, `registered`, `retested`, `improved`, `spend`.
```
CAC                 = spend / orders
cost_per_registered = spend / registered
cost_per_retest     = spend / retested          (headline)
retest_rate         = retested / orders
LTV_90d             = Σ(order_value) + Σ(membership_months_within_90d × 49)
```
Leaderboard has a single toggle: **Rank by followers** ↔ **Rank by cost-per-retest**. The reorder is animated. The synthetic data must make this toggle tell the story (see §12).

### 8.8 Thompson-sampling allocator
- One Beta(α, β) per active campaign over retest-per-order. Prior α=1, β=1 (or informed by segment average).
- Weekly run: sample θ_i ~ Beta(α_i, β_i); allocation_i = budget × θ_i / Σθ, with a 5% floor per campaign for exploration and a cap of 40%.
- Persist posterior + allocation to `allocator_runs`. UI shows each campaign's distribution as a small density curve, the sampled draw as a marker, and this week's allocation vs last week's.
- Tests: allocations sum to budget, floors/caps respected, posterior updates with observed data, deterministic under a seeded RNG.

## 9. Intelligence (`/lib/intelligence`, `/api/aggregates`)

All aggregates go through one function `guardedAggregate(query)` that:
1. Filters to `consent_research = true`.
2. Groups by the requested dimensions (`segment`, `region_state`, `age_band`, `sex`, `month`, `plan`, `channel`).
3. Drops any cell with `count < MIN_COHORT` and returns it as `{ suppressed: true }`.
4. Never returns row-level data. There is no other read path for intelligence.

Views:
- **Prevalence map:** primary segment share by state (choropleth or a simple state grid); cells under threshold shown hatched "insufficient data".
- **Intervention → marker delta:** for customers with outcomes, mean change per marker grouped by intervention type; sample size shown on every bar.
- **Retention by channel × plan:** retest rate.
- **Coverage heatmap:** count per (segment × age_band × region) — this drives where study-tier recruitment and creator seeding should go.
- **Guardrails widget:** consent rate, `MIN_COHORT` setting (editable, persists to `settings`), and an "Export aggregates (CSV)" button that only ever emits guarded cells. A disabled "Export rows" control with tooltip "Row-level export does not exist in this system."

Tests: guard suppresses cells below threshold; changing the setting changes suppression; the export endpoint cannot be coerced to return rows.

## 11. Model (`/model`) — the path to $1B as a calculator

Inputs (sliders, defaults in parentheses): new customers/month (800), monthly growth in new customers (4%), pricing model (`standalone` | `membership_first` | `study`), retest rate (35%; auto-set per plan: 22% / 58% / 71% unless overridden), monthly membership churn after month 3 (8%), brand-portal take rate on partner GMV (15%), partner GMV per retested customer per year ($120), horizon (36 months), valuation multiple on ARR (12×, range 6–25×).

Formulas (keep in `/lib/model`, unit-tested):
```
kit_revenue_m        = new_m × kit_price(plan)            // 249 | 99 | 149
members_m            = members_{m-1} × (1 − churn) + new_m × join_rate(plan)   // 0.25 | 1.0 | 1.0
membership_rev_m     = members_m × 49
retested_cum         = Σ new_m × retest_rate
dataset_size         = retested_cum                        // labeled outcome tuples
brand_rev_m          = (retested_cum / 12) × partner_gmv_per_year / 12 × take_rate  // ramps from month 18
ARR_m                = 12 × (kit_revenue_m + membership_rev_m + brand_rev_m)
valuation_m          = ARR_m × multiple
```
Outputs update live: members, ARR, dataset size, brand revenue, implied valuation; a small note anchors the multiple range to public comparables (Function Health: ~$2.5B valuation on a reported ~$100M+ run-rate) without asserting private numbers as fact.

Below the sliders: a Year 1 / Year 2 / Year 3 timeline. Each milestone links to the feature in the app that unlocks it (Year 1 → `/ops`, `/growth`; Year 2 → membership-first pricing + interventions; Year 3 → `/brand`, `/intelligence` export).

## 12. Synthetic data (`/lib/synthetic`, `supabase/seed.ts`)

Deterministic (`seedrandom('breakoutos-v1')`). Regenerating must produce identical data. Target: **500 customers**, 12 months of history ending "today".

- **Region:** US states weighted by population; make FL, TX, CA, NY, GA the top 5.
- **Age:** 16-19 8%, 20-24 27%, 25-34 40%, 35-44 18%, 45+ 7%. **Sex:** female 78%, male 20%, other 2%.
- **Channel:** instagram 40%, tiktok 20%, youtube 15%, search 15%, referral 7%, direct 3%.
- **Plan:** standalone 60%, membership_first 30%, study 10%. Retest rate by plan: 22% / 58% / 71%. Consent_research: 90% for study, 55% membership_first, 30% standalone.
- **Segment priors:** androgen 35%, insulin 25%, cortisol 20%, nutrient 12%, inflammation 5%, mixed 3%. Segment correlates with age (insulin skews 25+, androgen skews <30) and with channel weakly.
- **Biomarker generation:** draw each marker from a normal around a segment-specific center, then flag against reference ranges. Illustrative adult ranges for synthetic data only (not clinical guidance):
  - testosterone (ng/dL): female 15–70, male 300–1000
  - dhea_s (µg/dL): 35–430
  - shbg (nmol/L): female 20–130, male 10–57
  - cortisol AM (µg/dL): 6–23
  - insulin fasting (µIU/mL): 2–20, optimal < 10
  - vitamin_d (ng/mL): 30–100
  - zinc (µg/dL): 60–120
  - hs_crp (mg/L): < 1 low, 1–3 average, > 3 high
  Segment rules: androgen → high testosterone/DHEA-S, low SHBG; insulin → high insulin; cortisol → high cortisol; nutrient → low vitamin D and/or zinc; inflammation → high hs-CRP; mixed → two of the above.
- **Retests:** for retested customers, generate a second panel at day 85–110 with markers moved toward optimal for the segment's drivers 60–75% of the time; compute `outcomes`.
- **Kits & states:** most kits progress through the happy path with realistic dwell times; **~8% of kits sit in exception or stuck states right now** (`results_locked` 3%, `backordered` 2%, `registration_mismatch` 1%, `shipped` past SLA 2%) so `/ops` has real work in it on demo day.
- **Tickets:** ~60 open/recent tickets whose bodies paraphrase the real complaint patterns (results ready but portal says kit ID invalid; secure link redirects to sign-in; ordered weeks ago, no shipping notice; parent ordering for a minor, birthday rejected; refund request citing the 90-day guarantee; question about a cortisol result). Write original text; do not copy any real review.
- **Creators:** 40 from the live YouTube pull (run once, then cached in the seed as a snapshot for reproducibility, with `data_status='live'` only when the running build re-fetches successfully) + 30 seeded Instagram/TikTok creators with plausible names and handles. Assign 15 campaigns with codes and spend $300–$6,000.
- **Attribution story (must be true in the data):** at least one large creator (300–500K followers) with strong orders but a retest rate under 10% (young audience, standalone plan), and at least one small creator (40–80K) with fewer orders but a retest rate over 50% (25–34, hormonal-acne content, membership_first). The leaderboard toggle must flip their order.
- **Names:** realistic first names only; `email_masked` like `m***@gmail.com`.

## 14. Design direction (follow exactly; this is a designed product for a founder who listed "an eye for UI polish" in the posting)

Spend boldness there; keep everything else quiet.

**Tokens (`/app/globals.css` as CSS variables):**
- `--bg` #12222E (deep petrol; not near-black)
- `--surface` #1A2F3D
- `--raised` #223B4B

- `--text` #E9F0F3
